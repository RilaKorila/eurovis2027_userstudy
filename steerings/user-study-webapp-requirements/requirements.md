# 静止画Graph View比較実験：Webアプリ要件書

作成日：2026-11-18  
用途：別repository・別agentで作る、今回のuser study専用Webアプリの実装引継ぎ。

## 1. 目的と確定事項

前後2時刻のグラフ画像を使う課題で、3種類のGraph View描画条件を比較する。取得したい指標は**正答率、回答時間、自信度**の3つ。

- 参加者は開始時に、事前に研究者から指定された**Group A / Group B / Group C**を選ぶ。
- グループは**問題ごとの描画条件の割当**を切り替える。グループ内ですべて同じ描画条件に固定しない（ユーザー確認済み）。
- 1人が解くのは**練習1問＋本番5問＝計6問**。同じ本番問題を3条件で繰り返し解かせない。
- 本番の画面遷移は**確認 → グラフ画像と回答 → 自信度 → 休憩**。これを5問分繰り返す。
- 回答時間は、**グラフ画像が表示された時点から、回答を確定して次の画面へ進む操作を受け付けた時点まで**。自信度の回答時間、確認、休憩、画像の読込待ちは含めない。
- 最後に、練習と本番の記録を**まとめて1回送信**する。途中の回答操作のたびにSpreadsheetへ送信しない。
- 技術スタックは未指定。Streamlit、Next.js等でよい。保存先もSpreadsheet等の簡単な構成でよい。
- 本番参加者は最大15名程度を想定する。大規模な認証・管理システムは作らない。

本書の画面・計測仕様を優先し、過去repositoryの研究計画にある試行数や実験方式をそのまま移植しない。

## 2. 問題と刺激画像

### 2.1 問題数と必要ファイル

ユーザーが選定した5つを**本番の5つの問題（Q1〜Q5）**として扱う。各問題に3描画条件の画像を用意する。

| 種別 | 問題数 | 各問題の画像 | 必要画像数 |
|---|---:|---:|---:|
| 練習 P0 | 1 | 全グループ共通1枚 | 1 |
| 本番 Q1〜Q5 | 5 | 描画条件L1/L2/L3の3枚 | 15 |
| 合計 | 6 | | 16 |

選定した5枚のファイル名・実体は、まだ本アプリ要件には提供されていない。実装agentは例示用のplaceholderで画面を作れるが、画像・設問・正解を推測して確定しない。実験開始前に実ファイルへ差し替える。

本番問題間で設問は違ってよい。同じ問題の3描画条件間では、**元グラフ、CD所属、対象イベント、設問、選択肢、正解、色、注記、画像寸法、線の濃さ**を共通にし、描画条件に由来する配置だけを変える。CDは問題／datasetごとに適切なものを選んでよい。Smoothed Graphに限定しない。

### 2.2 画像表示・回答形式

- 1画像に前後2時刻と必要なP/P1/P2、A〜D等の注記を含めてよい。アプリ側で設問・回答ボタンを別に表示する。
- PNG等の画像は静止画として扱い、graphのノード移動、パン、拡大縮小、hover操作は実装しない。
- 問題文と「つながる」の定義などは設定ファイルのテキストを使う。
- 回答は**A〜Dから1つ選択**する4択。初期選択なし。選択前は「回答を確定して次へ」を押せない。
- 選択直後には遷移せず、確定前なら選び直せる。確定した後は前問・前画面に戻って回答を修正できない。
- 画像自体に回答欄・確定ボタンが描かれている草案を、そのまま操作UIとして使わない。実験用画像では重複する疑似UIを取り除く。画像に正解や「正解B」等の解説を含めない。
- 本番中に正誤・点数・正解のヒントを表示しない。

### 2.3 条件名とグループ名を区別する

- `group_id`: A / B / C。参加者が選ぶ、割当表の識別子。
- `layout_condition_id`: L1 / L2 / L3。描画アルゴリズムの識別子。
- `option_id`: A / B / C / D。問題の回答ラベル。

この3つを同じ変数や同じ集計列として扱わない。参加者に描画アルゴリズム名・「提案手法」等を表示しない。研究者が設定するL1〜L3の実アルゴリズム対応は保存する。

## 3. Group A〜Cの割当

初期実装は次の固定表を使う。条件対応と割当表は設定で差し替え可能にする。

| 本番提示位置／問題 | Group A | Group B | Group C |
|---|---|---|---|
| 1：Q1 | L1 | L2 | L3 |
| 2：Q2 | L2 | L3 | L1 |
| 3：Q3 | L3 | L1 | L2 |
| 4：Q4 | L1 | L2 | L3 |
| 5：Q5 | L2 | L3 | L1 |

- 1人あたり5問なので条件数は2/2/1になる。この不均衡を隠さず記録する。
- 3グループに同人数を割り当てると、各問題はL1/L2/L3で同数提示される。全体の条件数も均衡する。
- 15名なら、名簿は原則各Group5名とする。人数管理・割当自体は研究者が事前名簿で行い、アプリは自動でグループを選ばない。
- 練習はグループ共通。練習用画像は本番とは別問題にする。
- 初期実装ではQ1→Q5の固定順とする。無断でランダム化しない。これは提示順を完全に均衡化した設計ではない。順序変更が必要な場合は、研究者が割当表の各行を変更し、実際の提示位置を保存する。
- 選択肢ラベル・画像をクライアントで無作為に入れ替えない。必要なラベル変更は画像と正解を整合させて事前に設定する。

## 4. 画面フロー

```text
開始・Group選択
  → 説明
  → 練習開始確認
  → 練習画像・回答
  → 練習の自信度
  → 練習の正解・解説
  → 本番Q1の確認
      → グラフ画像・回答
      → 自信度
      → 休憩
  → 本番Q2の確認 → 画像・回答 → 自信度 → 休憩
  → 本番Q3の確認 → 画像・回答 → 自信度 → 休憩
  → 本番Q4の確認 → 画像・回答 → 自信度 → 休憩
  → 本番Q5の確認 → 画像・回答 → 自信度 → 休憩
  → 全回答の送信確認
  → 一括送信
  → 完了
```

### 4.1 開始・Group選択

- 表示名は「Group A」「Group B」「Group C」のみ。選択必須、初期選択なし。
- 「事前に指定されたグループを選んでください」と表示する。
- 匿名の`participant_id`と`session_id`を生成する。氏名・メールアドレスの入力は初期実装に含めない。
- 練習開始前までグループを変更できる。練習開始後は変更不可。
- Groupを選んだ時点で割当表と設定versionをセッションへ固定する。
- 名簿との個人単位の照合が必要なら、研究者が配る匿名参加者コードを追加する余地を設ける。ただし初期必須画面を増やさず、実装者が名簿の氏名を取り込まない。

### 4.2 説明

以下を短く説明する。

1. 練習1問、本番5問であること。
2. 前後2時刻の図を見比べて、回答を1つ選ぶこと。
3. 接続等の課題固有の用語。
4. 回答後に自信度を答えること。
5. 各問後は自分のペースで休憩できること。
6. 最後の送信ボタンまで押して完了すること。

この画面では本番画像や本番の正解を見せない。

### 4.3 練習（1問）

- 本番と同じ画像表示・回答・自信度操作を練習する。
- 練習だけは、自信度回答後に正解と短い解説を表示する。
- 練習の回答・時間・自信度も記録するが、`is_practice=true`として本番集計から除外する。
- 初期実装では合否判定・強制反復・練習問題追加はしない。説明を読んで本番へ進める。

### 4.4 本番の確認画面

- 「本番 第n問／5」と「準備ができたら開始してください」を表示する。
- 本番の画像、具体的な設問・選択肢をまだ見せない。一般的な操作案内は表示可。
- 「問題を開始する」ボタンを置く。
- この画面中に対象画像を先読みしてよい。ただし画面・スクリーンリーダー・代替テキストに問題内容を先出ししない。
- 読込中はボタンを無効にし、画像を表示可能になってから開始できるようにする。

### 4.5 グラフ画像・回答画面

- 問題番号、設問、定義、グラフ画像、A〜Dの選択肢、「回答を確定して次へ」を表示する。
- 実験条件名、正解、他の問題の回答、回答時間のカウントダウンは表示しない。
- 画像・設問・選択肢が表示された時点から計時する。
- 回答を1つ選び、確定操作が受理された時点で計時を止める。そのまま自信度画面へ進む。
- 回答の選択だけでは計時を止めない。確定直前までの選び直しも回答時間に含める。
- 初期実装に時間制限・自動確定は設けない。

### 4.6 自信度画面

質問文：**「今の回答に、どのくらい自信がありますか？」**

初期実装は5件法とする。

| 保存値 | 表示 |
|---|---|
| 1 | まったく自信がない |
| 2 | あまり自信がない |
| 3 | どちらともいえない |
| 4 | やや自信がある |
| 5 | とても自信がある |

- 単一選択、初期選択なし、回答必須。
- グラフ画像・問題の回答選択肢は再表示しない。正誤を表示しない。
- 「次へ」で自信度を確定し、休憩画面へ進む。
- 自信度画面で過ごした時間を、グラフの回答時間に加算しない。

### 4.7 休憩画面

- 「第n問が終了しました。必要に応じて休憩してください」と表示する。
- 待ち時間の下限・上限、自動遷移は設けない。
- Q1〜Q4では「次の問題へ」で次の確認画面へ進む。ここで次問の計時を開始しない。
- Q5後も休憩画面を表示し、「送信確認へ」で最終確認画面へ進む。
- 前問・次問の画像、正誤、得点は表示しない。

### 4.8 送信確認・送信・完了

- 「本番5問の回答と自信度が揃いました。送信して終了してください」と表示する。
- 選択したGroupと回答件数を示す。回答の修正や正誤表示はしない。
- 「回答をまとめて送信」で、練習1問、本番5問、計測補助ログを1セッション分のpayloadとして送る。
- 送信中はボタンを無効にし、二重送信を防ぐ。
- 保存先から保存完了の応答を受けて初めて「送信が完了しました。ご協力ありがとうございました」と表示する。
- 失敗時は回答を保持し、「再送信」で同じpayloadを送れる。回答を最初からやり直させない。
- 送信成功後に再読込しても再送信しない。保存済みの完了状態を表示する。
- 完了画面でも正答率・正解・研究仮説を表示しない。

## 5. 回答時間の計測要件

このstudyの主要な実装要件。**サーバーで画面処理を開始した時刻と、サーバーが回答を受信した時刻の差を使わない。**

### 5.1 起点・終点

| 項目 | 定義 |
|---|---|
| 起点 | 画像の読込・decodeと、設問・回答UIの準備が済み、参加者に表示された最初の描画フレームに合わせて取得するクライアント時刻 |
| 終点 | 「回答を確定して次へ」の有効な操作をクライアントが受理した時刻 |
| 保存値 | `response_time_ms = ended_monotonic_ms - started_monotonic_ms` |

- 同じブラウザ内の単調時計を使う（例：`performance.now()`）。ミリ秒で保存し、表示・分析で秒へ変換する。
- `Date.now()`等の壁時計は監査用のUTC日時には使えるが、回答時間の差分計算には使わない。
- 開始ボタンを押してから画像が読み込まれるまでの待ち時間を含めない。
- 終点は次画面へ進むクリックの受理時とする。次画面のサーバー応答待ち・保存待ちを含めない。
- 設問文も計時中に初めて提示するため、読解時間は回答時間に含まれる。条件間で設問文を共通にする。
- 画像とボタンの描画順で、画像だけが先に見えて時計が始まらない時間を作らない。描画待ちの状態と回答可能状態を制御する。
- 画像・UI表示後の再描画、ラジオボタンの選択変更、Streamlitのrerun等で起点をリセットしない。
- 有効な確定操作は一度だけ受理し、その時刻と回答を固定する。

### 5.2 画像の読込・表示サイズ

- 各条件の画像を同じ表示領域・縮尺の規則で表示し、縦横比を保つ。画像端・注記を切り取らない。
- 本番はPCでの利用を前提とする。グラフ画像全体、設問、回答UIを横スクロールなしで表示する。
- 1500×900程度の画面を初期確認対象とし、最終の画像寸法に応じて必要最小viewportを設定で指定できるようにする。
- 必要最小viewportを満たさない場合は確認画面で案内し、問題を開始しない。実験用の小さなスマートフォン表示を新規設計する必要はない。
- 最終画像・使用端末で、ノード・線・回答ラベルが読み取れることを研究者が確認する。画像を縮小して読めなくすることをレスポンシブ対応と扱わない。
- 自然画像サイズ、実際の表示サイズ、viewport、device pixel ratioを記録する。
- 画像の読込失敗時は計時を始めず、再試行を出す。

### 5.3 タブ移動・リロード

- 回答中にタブが非表示になった／ウィンドウがfocusを失った場合は、その回数・時刻を補助ログへ記録する。
- タブ移動中も主たる経過時間は継続し、勝手に差し引かない。後の分析で扱いを決められるようにする。
- リロード・通信切断で別画面へ進む途中の回答が消えないよう、確定済み回答と現在stateをブラウザ内に保存する。
- 問題表示中にリロードした場合、以前の`performance.now()`を新しいページと差し引かない。未確定attemptを`aborted_reload`として記録し、同じ問題の確認画面から再開する。
- この再開は画像の再提示になるため、`repeated_exposure=true`とattempt番号を記録する。通常の初回回答と黙って混ぜない。本番5問という数を増やさず、同じ問題への再試行として扱う。
- 自信度画面でのリロードでは、確定済み回答・時間を保持して自信度から再開する。

## 6. 記録するデータ

### 6.1 セッション単位

- `study_version`、`stimulus_manifest_version`、`assignment_version`
- `participant_id`（匿名）、`session_id`、任意の`participant_code`
- `group_id`
- `started_at_utc`、`submitted_at_utc`（クライアント）、`received_at_utc`（サーバー）
- 実際に使った割当表のsnapshot
- `status`（in_progress / submitted）
- browser / viewport等の計測環境
- 全trial recordsと中断attempt records
- `submission_id`（再送でも変わらない識別子）

### 6.2 試行単位

| 列 | 内容 |
|---|---|
| `trial_id` | セッション内で一意 |
| `question_id` | P0 / Q1〜Q5 |
| `is_practice` | 練習ならtrue |
| `trial_index` | 本番提示位置1〜5、練習は0 |
| `layout_condition_id` | L1/L2/L3、練習はpractice |
| `stimulus_id` / `stimulus_sha256` | 実際に表示した画像の識別子とhash |
| `dataset_id` / `event_id` | 研究者が設定した出典識別子 |
| `source_timestamp` / `target_timestamp` | 対象の前後時刻 |
| `selected_option_id` | A/B/C/D |
| `correct_option_id` | 正解（研究者設定から採点側で付与） |
| `is_correct` | 選択と正解が一致するか |
| `response_time_ms` | 定義した回答時間 |
| `confidence` | 1〜5 |
| `image_shown_at_utc` / `answer_confirmed_at_utc` | 監査用時刻 |
| `attempt_index` / `repeated_exposure` | 再試行の有無 |
| `hidden_count` / `blur_count` | 回答中のタブ非表示・focus喪失回数 |
| `image_natural_width/height` | 画像の元サイズ |
| `image_rendered_width/height` | 表示サイズ |
| `viewport_width/height` / `device_pixel_ratio` | 表示環境 |

研究者が後から問別・条件別・グループ別・参加者別に集計できること。`group_id`だけ保存して、どの問題をどの条件で見たか復元できない実装は不可。

## 7. 一括送信とSpreadsheet保存

- 回答は最後の送信まではブラウザ内に保持する。Spreadsheet等への永続送信は最後の1セッション単位。
- クライアントからのpayloadに正解を含めない。本番の正解はサーバー側設定から取得し、サーバーで正誤を付与する。練習の正解・解説だけはブラウザで表示してよい。
- `group_id`、問題数、割当、画像識別子、選択肢、自信度の範囲、有限かつ非負の時間をサーバーで検証する。
- 本番5件＋練習1件が揃っていないpayloadを、完了済みセッションとして保存しない。
- 保存は`submission_id`で冪等にする。サーバーでは保存できたが応答が届かなかった場合、再送しても回答が増殖しない。
- 正常な通信遅延と失敗を区別し、保存完了応答を返すまで完了画面にしない。
- 保存先の認証情報はサーバー側の環境変数・secretsに置き、画像／公開JS／クライアント設定へ含めない。

Spreadsheetを使うなら、初期実装は**1セッション＝1行**に、`responses_json`とsession metadataを保存する方式でよい。1参加者の6件を6回appendして途中までしか保存されない状態を避ける。Spreadsheetに一意制約はないので、送信処理の直列化と既存`submission_id`確認など、再送・同時送信への対処を保存用backendで実装する。

研究者には、保存済みJSONから**1本番回答＝1行**のCSVへ展開できる簡単なexport手段を提供する。公開参加者画面から他参加者の結果を閲覧できる機能は作らない。

## 8. 集計できるもの

Webアプリ内に研究者用dashboardや統計検定を作る必要はない。CSV等で次の集計が可能な記録を残す。

1. **正答率**：本番の`is_correct`を集計。まず参加者×描画条件別、および問題×描画条件別に算出できること。
2. **回答時間**：本番の`response_time_ms`を秒へ変換。全回答の時間を保持し、正答だけの時間も後から抽出可能にする。
3. **自信度**：本番の1〜5を保持。参加者×描画条件、問題×描画条件別の分布・中央値を計算できること。

- 練習を本番集計へ含めない。
- 条件の出現数が1/2/2なので、1人の正解数そのものを条件間で比べず、試行数を分母にする。
- 時間の極端値、タブ移動、リロードした回答を自動で削除しない。raw記録とflagを保存し、分析側で事前に決めた規則を適用する。
- 5問×15名＝75本番回答は、独立した75人分のデータではない。参加者ID・問題IDを保持する。
- 最終的な統計検定・除外基準の確定はこのWebアプリ実装の対象外。

## 9. 設定ファイルと実装の分離

実装コードを書き換えずに以下を差し替えられるようにする。

- 練習1問、本番5問の設問、定義、選択肢、画像、出典metadata。
- L1/L2/L3と実際の描画アルゴリズム名の対応。
- Group A/B/Cの提示順・描画条件割当。
- サーバー側の正解表、練習解説。
- 自信度の文言、案内文。
- 表示サイズの要件、study/manifest/assignmentのversion。
- 保存先設定（秘密情報は公開設定と別管理）。

引継ぎ用に`study-config.example.json`を同梱した。画像・dataset/event・時刻はplaceholderであり、正式刺激の決定を意味しない。正解の記載例は別ファイル`answer-key.example.json`に置く。本番の正解表を参加者へ配信しない。

起動時に、全Groupに本番5問があり、Q1〜Q5が各1回、必要画像が存在し、正解が有効な選択肢で、versionが設定されていることを検証する。本番用のplaceholderが残っていたら、参加者用study開始を許可しない。開発previewのみplaceholderを許可する。

## 10. 技術方針

使い捨ての小規模アプリなので、要件を満たす最小構成でよい。

- **Streamlit案**：画面・状態管理・保存をStreamlitで実装してよい。ただし計時はブラウザ内で行う。標準widgetのサーバー受信時刻やPythonの`time.time()`だけで計測しない。rerunで起点が変わらない実装を用意する。
- **Next.js等の案**：ブラウザ側stateと単調時計、最後の送信用server endpointという構成でよい。画像を事前にdecodeしてから表示する。
- 保存先はGoogle Sheets等のSpreadsheetでよい。Webアプリが認証情報を持つserverを介して送信する。
- アカウント作成、参加者ログイン、graphの再計算、CD実行、描画アルゴリズム実行、実験途中の画像生成は不要。完成した画像と設定を配信するだけ。
- インターネット上の画像生成APIやこの研究repositoryのローカルパスに実行時依存しない。必要な画像・manifestを新repo側へ配置する。

実装agentはスタックと公開先をREADMEに記載し、実計測仕様・一括送信・再送を満たすことを優先する。

## 11. 受入条件・確認項目

### 画面と割当

- [ ] Groupを未選択で開始できず、Group A〜Cを表示できる。
- [ ] 各Groupの割当が表どおりで、1人に練習1問＋本番5問だけ提示する。
- [ ] 本番の同じ問題を同じ参加者に別条件で再出題しない（中断再試行はflag付き）。
- [ ] 練習だけ正解・解説を表示し、本番は正解・描画条件名を表示しない。
- [ ] 本番で「確認→画像・回答→自信度→休憩」が5回実行され、その後一括送信できる。
- [ ] 回答・自信度の初期選択がなく、未選択で進めない。
- [ ] 確定後に戻って回答を変更できない。

### 計時

- [ ] 画像の読込を意図的に遅らせても、読込待ちが回答時間に含まれない。
- [ ] 開始確認や休憩で待っても、回答時間に加算されない。
- [ ] 回答を選び直しても、計時の起点が変わらない。
- [ ] 回答確定後に自信度で長く待っても、回答時間は変わらない。
- [ ] サーバー応答を遅らせても、その待ち時間が回答時間に入らない。
- [ ] タブ移動をflagとして残し、リロードで負の時間や別ページの時計差を作らない。
- [ ] 実際の問題画像・想定端末で画像全体と回答UIを視認できる。

### 保存

- [ ] 途中の回答操作ではSpreadsheetへ送信せず、最後に1セッション分をまとめて送る。
- [ ] 練習1件＋本番5件について、回答・正誤・時間・自信度・問題・条件・順序を復元できる。
- [ ] 正答と誤答の両方が正しく採点される。
- [ ] 連打、再送、保存直後の通信切断で同一submissionが重複しない。
- [ ] 送信失敗時に回答を失わず、再送できる。
- [ ] 送信成功後の再読込で再送せず、完了を表示する。
- [ ] 画像・正解・割当設定の不整合や未設定placeholderを実験開始前に検出する。
- [ ] テストデータを本番参加者データと区別できる（別study_version／保存先等）。

## 12. 実験開始までに研究者が渡すもの

1. 本番5問の正式な設問・定義・選択肢・正解、およびdataset/eventの識別子。
2. 各問題の3描画条件の画像15枚と、共通練習画像1枚。
3. 練習の設問・正解・解説。
4. L1/L2/L3の実際のアルゴリズム対応。
5. 参加者のGroup A/B/C名簿（アプリへ氏名を取り込む必要はない）。
6. 保存先Spreadsheet等とserver側認証設定、公開先。
7. 研究者が確認した最終画像の表示寸法と、設定version。

これらが未提供でもアプリの枠組みは作れる。正式刺激・正解を実装agentが既存画像から推定して埋めることはしない。
